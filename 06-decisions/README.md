# 06. Архитектурные решения (ADR)

**Вывод:** восемь решений, которые определили версию 2.0. Каждое описано по шаблону «контекст → решение → альтернативы → последствия», чтобы через год было понятно не только что сделано, но и почему.

| # | Решение | Главная причина |
|---|---|---|
| [0001](ADR-0001.md) | Чистое доменное ядро: формула баланса в одном месте | Баланс считался в четырёх местах: в модели данных, сервисе, интерфейсе и экспорте |
| [0002](ADR-0002.md) | Слоистая архитектура: интерфейс → сервисы → репозиторий | В прототипе окна интерфейса напрямую выполняли SQL |
| [0003](ADR-0003.md) | Общий PostgreSQL в сети больницы | Врачи работают с нескольких ПК, данные пациента должны быть одинаковыми на всех рабочих местах |
| [0004](ADR-0004.md) | Оптимистичная блокировка и серверное время | Одну запись могут открыть два врача на разных ПК |
| [0005](ADR-0005.md) | Журнал изменений на триггерах БД и разделение ролей | Медицинские данные требуют ответственности за каждую правку, в том числе сделанную мимо программы: через администрирование БД или скрипты |
| [0006](ADR-0006.md) | Поэтапная миграция живой прод-схемы | В проде уже были данные пациентов, возможны дубли дат и подозрительные значения |
| [0007](ADR-0007.md) | Переход на PySide6 по утверждённому дизайну | Прототип на tkinter состоял из отдельных окон с проблемами обновления состояния, плохо масштабировался и выглядел устаревшим |
| [0008](ADR-0008.md) | Воспроизводимая сборка, защищённая конфигурация и демо-редакция | Программу ставят на рабочие ПК без Python |
